Cross-chain swaps are non-atomic as they span two chains and a bridge provider in between. If the origin transaction succeeds but the bridge cannot complete, the user's funds have left their wallet and need to be recovered.

This page explains what happens when a bridge fails, how recovery works, and what your integration should do for each scenario. For the happy-path status lifecycle, see [Tracking Transaction Status](/cross-chain/cross-chain-api/key-concepts/tracking-transaction-status).

## Origin refund vs dest retry vs dest claim

Three different recoveries can follow a failed bridge. Do not treat them as the same thing.

**Origin refund.** The bridge returns tokens on origin (or dest USDC for Mayan MCTP / FastMCTP). Status moves `refund_pending` → `refund_succeeded`. The bridge provider runs this. Keep polling `/status`.

**Dest retry.** Origin already locked, burned, or posted the message. Dest execution failed. A dest retry completes dest delivery in the bridge step's `buyToken`. It does not mint an origin refund. 0x submits dest retries for the bridges marked "0x dest retry" below. Keep polling. A dest retry that lands becomes `bridge_filled`. If dest never lands, status stays `manual_action_required` except on Arbitrum Bridge, which can become `failed` after `deadline`. Contact 0x with the `zid` if it stays stuck.

**Dest claim.** Dest already filled. A dest swap after fill failed. Tokens sit in a dest contract the recipient owns. `/status` returns `manualTransaction`. The recipient must sign it on `recovery.chainId`. 0x cannot submit that tx.

## How Failures Surface

When you poll `GET /cross-chain/status` and the response has `status: "bridge_failed"`, it includes a `failure` object with everything needed to understand what went wrong and what to do next.

Do not stop polling on `bridge_failed` while `failure.status` is `refund_pending` or `manual_action_required`. A dest retry that lands flips the top-level status to `bridge_filled` and drops the `failure` object.

## Failure Object Structure

```json
{
  "status": "bridge_failed",
  "bridge": "across_v4",
  "failure": {
    "reason": "expired",
    "status": "refund_pending",
    "transactions": [
      { "chainId": 8453, "txHash": "0xabc...", "timestamp": 1712345678 }
    ],
    "recovery": {
      "chainId": 8453,
      "token": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "amount": "2500000000",
      "estimatedTimeSeconds": 1200,
      "deadline": null,
      "manualTransaction": null,
      "settledAmount": null
    }
  }
}
```

## Failure Reasons

| Reason | Meaning |
| --- | --- |
| `expired` | The bridge provider is unable to execute the cross-chain transaction before its expiry. |
| `cancelled` | The bridge has been cancelled by the user or a third-party entity. This can occur only if someone bypasses 0x's recommended flow and interacts directly with the bridge provider's system, or if the bridge provider experiences a technical failure. |
| `out_of_gas` | The dest call ran out of gas. For dest-retry bridges, 0x retries dest. Keep polling. |
| `internal` | The bridge provider ran into a technical failure. For dest-retry bridges, 0x retries dest. Keep polling. |
| `unknown` | The reason of the bridge failure cannot be determined by 0x. |

## Failure Statuses

| Status | Description |
| --- | --- |
| `refund_pending` | An automatic refund has been initiated by the bridge provider. Keep polling. |
| `refund_succeeded` | The refund has been issued. The user receives the funds in `originAddress` or `destinationAddress`. Check `failure.recovery` for chain, token, and `settledAmount`. |
| `manual_action_required` | Dest is incomplete. Dest retry: 0x submits, `manualTransaction` is omitted, keep polling. Dest claim: `manualTransaction` is present, the recipient must sign it. `/status` does not track a transaction you submit yourself. |
| `no_actions_required` | The bridge failed before transferring tokens from origin. Funds never left. No further action. |
| `failed` | Terminal. The user cannot recover from here. Contact 0x with the `zid`. |

## Recovery Step Fields

| Field | Type | Description |
| --- | --- | --- |
| `chainId` | number | Chain where recovery occurs. Dest for dest retries and dest claims. Origin (or dest for Mayan MCTP / FastMCTP) for refunds. |
| `token` | string | Token recovered or delivered. Dest retries complete dest in the bridge step's `buyToken`. Origin refunds return the bridge step's `sellToken` (USDC for Mayan MCTP / FastMCTP dest refunds). May differ from the quote `sellToken`. |
| `amount` | string | Expected recovery amount (bigint). |
| `estimatedTimeSeconds` | number or null | Seconds until automatic refund. Present when `refund_pending`. |
| `deadline` | number or null | Unix timestamp. Only Arbitrum Bridge. Display it. After this time status can become `failed` and funds may be lost. 0x attempts dest a few times. It does not keep retrying until the deadline. |
| `manualTransaction` | object or null | Ready-to-sign dest claim. Present only when the recipient must sign. Null when 0x submits dest retries, and when no tx is available (CCIP). |
| `settledAmount` | string or null | Actual refunded amount. Populated after a refund confirms. May differ from `amount`. |

## What your integration should do

1. Poll `/status`.
2. If `failure.status` is `refund_pending` or `refund_succeeded`, treat it as a refund. Do not ask the user to sign dest.
3. If `failure.status` is `manual_action_required` and `manualTransaction` is `null`, keep polling. For dest-retry bridges in the table, 0x submits dest. Do not prompt the user to sign. If it stays here, contact 0x with the `zid`. Only Arbitrum Bridge can move to `failed`.
4. If `manualTransaction` is present, the recipient signs it on `recovery.chainId`. This is a dest claim. 0x cannot submit it.
5. If `failure.status` is `failed`, contact 0x with the `zid`.

## Refund Token and Chain

The refund token and chain depend on **where the failure happened** and **what the route looked like**. The refund is not always in the user's original `sellToken` on `originChain`. What you get back depends on the bridge (see table below) and the route composition.

The main thing to understand: the refund token is based on the **bridge step's** sell or buy token and not the route's `sellToken`. If the route included a swap or wrap before the bridge, the bridge step's tokens differ from what the user started with:

| Route | Sell token | Bridge token | Token refunded (origin-side bridges) |
| --- | --- | --- | --- |
| USDC → bridge | USDC | USDC | USDC |
| ETH → wrap → WETH → bridge | ETH | WETH | WETH (not ETH) |
| ETH → swap → USDC → bridge | ETH | USDC | USDC (not ETH) |

The `recovery.token`, `recovery.chainId`, and `recovery.amount` fields contain the exact details. For dest retries those fields describe dest delivery, not an origin refund.

## Manual Recovery Transactions

`manualTransaction` is omitted for dest retries 0x submits. Do not build a dest retry yourself when the field is null.

When `manualTransaction` is present, it is a dest claim. The recipient must sign it. 0x cannot submit it. Anyone else sending it reverts.

**EVM:**

```json
{ "chainType": "evm", "to": "0x...", "data": "0x...", "value": "0", "gas": "200000", "gasPrice": "30000000000" }
```

Submit via `eth_sendTransaction` on chain `recovery.chainId`.

**Solana:**

```json
{ "chainType": "svm", "serializedTransaction": "<base64>" }
```

Base64-decode, sign, submit.

- The recipient must sign. This is not an anyone-can-submit dest retry.
- If `deadline` is set, that field is for Arbitrum dest retry, not dest claim.

## Tracking Refund Progress

For automatic refunds, keep polling `/status`:

1. `bridge_failed` + `refund_pending` - refund initiated
2. `bridge_failed` + `refund_succeeded` - refund confirmed, `failure.transactions` has refund tx hash and `recovery.settledAmount` has actual refunded amount

## Tracking Dest Retry Progress

For dest retries 0x submits, keep polling `/status`:

1. `bridge_failed` + `manual_action_required`, `manualTransaction` null - dest retry in progress
2. `bridge_filled` - dest landed. The `failure` object is gone
3. Still `manual_action_required` after a while - dest did not land. Contact 0x with the `zid`. Only Arbitrum Bridge can move to `failed` after `deadline`.

## Recovery Behavior by Bridge

In this table, "bridge step's sell/buy token" refers to the tokens on the bridge step specifically - not the user's original `sellToken`/`buyToken` from the quote request. If the route included a swap or wrap before the bridge, these are different. See [Refund Token and Chain](#refund-token-and-chain) above.

| Bridge | Recovery | Chain | Token |
| --- | --- | --- | --- |
| Across V4 | Automatic origin refund | Origin | Bridge step's `sellToken` |
| Arbitrum Bridge | 0x dest retry (has deadline) | Destination | Bridge step's `buyToken` |
| Circle Forwarder | 0x dest retry | Destination | Bridge step's `buyToken` |
| CCIP | Dest retry (contact 0x) | Destination | Bridge step's `buyToken` |
| Gas.zip | Automatic origin refund | Origin | Bridge step's `sellToken` |
| HyperCore Bridge | Not tracked | - | - |
| Linea Bridge | Not tracked | - | - |
| Mayan Swift | Automatic origin refund | Origin | Bridge step's `sellToken` |
| Mayan MCTP / FastMCTP | Automatic dest refund | Destination | USDC |
| NEAR Intents | Automatic origin refund | Origin | Bridge step's `sellToken` |
| OFT (LayerZero) | 0x dest retry | Destination | Bridge step's `buyToken` |
| PAXG | 0x dest retry | Destination | Bridge step's `buyToken` |
| Relay | Automatic origin refund | Origin | Bridge step's `sellToken` |
| Squid | Automatic origin refund | Origin | Bridge step's `sellToken` |
| Stargate V2 | 0x dest retry | Destination | Bridge step's `buyToken` |
| Superchain | 0x dest retry | Destination | Bridge step's `buyToken` |

<Warning>
**Arbitrum Bridge** is the only bridge with a recovery **deadline**. Display it. 0x attempts dest a few times. It does not keep retrying until the deadline. After `deadline`, status can become `failed` and funds may be permanently lost.
</Warning>

For bridges marked "Not tracked", the 0x status service does not track the recovery process. The bridge provider may still offer recovery through their own tools. Contact 0x support with the `zid` for assistance.

For CCIP, `/status` does not return a dest retry transaction and 0x does not submit dest. Contact 0x with the `zid`.

## Example: Dest Retry in Progress (Stargate)

A Stargate bridge delivering to Arbitrum (chain 42161) ran out of gas on destination. 0x submits dest. `manualTransaction` is omitted. Keep polling.

```json
{
  "failure": {
    "reason": "out_of_gas", "status": "manual_action_required",
    "recovery": { "chainId": 42161, "token": "0xaf88d065e77c8cC2239327C5EDb3A432268e5831", "amount": "2500000000",
      "manualTransaction": null }
  }
}
```

## Example: Arbitrum Bridge Deadline

0x attempts dest. Display `deadline`. Do not wait for a user-signed dest retry.

```json
{
  "failure": {
    "reason": "out_of_gas", "status": "manual_action_required",
    "recovery": { "chainId": 42161, "deadline": 1713000000, "manualTransaction": null }
  }
}
```

## Example: Dest Claim

Dest filled, then a dest swap failed. The recipient signs `manualTransaction`. 0x cannot submit it.

```json
{
  "failure": {
    "reason": "internal", "status": "manual_action_required",

      "manualTransaction": { "chainType": "evm", "to": "0x...", "data": "0x...", "value": "0", "gas": "200000", "gasPrice": "30000000000" } }
  }
}
```
